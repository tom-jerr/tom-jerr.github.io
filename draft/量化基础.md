## 一、权重量化：W8A8 / W4A16 / AWQ / GPTQ 差异对比

| 维度 | W8A8 (SmoothQuant/LLM.int8()) | W4A16 (GPTQ/AWQ) | AWQ | GPTQ |
|------|------------------------------|------------------|-----|------|
| **量化对象** | Weight + Activation 均 INT8 | Weight INT4/FP4, Activation FP16 | Weight INT4/FP4, Activation FP16 | Weight INT4/FP4, Activation FP16 |
| **核心思想** | 迁移 activation 难度到 weight（SmoothQuant） | 逐层/逐组寻找最优量化参数 | 基于 activation 幅度保护重要权重通道 | 利用二阶信息（Hessian）逐层补偿误差 |
| **校准数据** | 需要少量样本统计 activation scale | 需要 | 需要（保护 salient channels） | 需要（计算 Hessian） |
| **精度损失** | 较小（<1% perplexity） | 中等（2-4%） | 较小（优于 GPTQ） | 中等 |
| **推理速度** | 快（INT8 GEMM） | 极快（4-bit GEMM，如 Marlin/ExLlama） | 极快（同左，需 fuse scaling） | 极快 |
| **显存节省** | ~50% | ~75% | ~75% | ~75% |
| **关键局限** | Outlier 处理、对超大规模模型仍可能掉点 | 需要 dequant + gemm 或专用 kernel | 需 fuse per-channel scale 到 kernel | 对超大模型（>70B）误差累积 |

### 核心差异一句话总结：
- **W8A8**：解决 activation 量化难题，追求**全 INT8 推理**；
- **W4A16**：只压 weight，activation 保持 FP16，用**4-bit 专用 GEMM kernel**加速；
- **AWQ**：W4A16 的增强版，通过**保护 salient weight channels**（乘上 activation 幅度）来提升精度；
- **GPTQ**：W4A16 的另一种路线，通过**OBS（Optimal Brain Surgeon）**逐层补偿量化误差。

## 二、KV Cache 量化：Scale 设计详解

### 2.1 三种粒度对比

```python
import torch

def quantize_per_tensor(kv, eps=1e-6):
    """
    per-tensor: 整个 KV Cache 一个 scale
    优点：最简单，kernel 友好（一个常数 scale）
    缺点：不同 head/token 动态范围差异大，精度最差
    """
    scale = kv.abs().max().clamp_min(eps) / 127
    q = torch.round(kv / scale).clamp(-128, 127).to(torch.int8)
    return q, scale  # scale: scalar

def quantize_per_token(kv, eps=1e-6):
    """
    per-token: 每个 token 一个 scale
    对 [num_tokens, num_heads, head_dim]，在 heads*head_dim 上取 max
    """
    # kv: [num_tokens, num_heads, head_dim]
    scale = kv.abs().amax(dim=[1, 2], keepdim=True).clamp_min(eps) / 127
    q = torch.round(kv / scale).clamp(-128, 127).to(torch.int8)
    return q, scale  # scale: [num_tokens, 1, 1]

def quantize_per_token_per_head(kv, eps=1e-6):
    """
    per-token per-head: 每个 token 的每个 head 一个 scale
    精度与效率的最佳平衡点
    """
    # kv: [num_tokens, num_heads, head_dim]
    scale = kv.abs().amax(dim=-1, keepdim=True).clamp_min(eps) / 127
    q = torch.round(kv / scale).clamp(-128, 127).to(torch.int8)
    return q, scale  # scale: [num_tokens, num_heads, 1]

def quantize_per_channel(kv, eps=1e-6):
    """
    per-channel: 每个 head 的每个 channel (head_dim) 一个 scale
    对 weight 常用，但对 dynamic KV Cache 在长上下文下不稳定
    """
    # kv: [num_tokens, num_heads, head_dim]
    # 假设在 num_tokens 维度上统计
    scale = kv.abs().amax(dim=0, keepdim=True).clamp_min(eps) / 127
    q = torch.round(kv / scale).clamp(-128, 127).to(torch.int8)
    return q, scale  # scale: [1, num_heads, head_dim]
```

### 2.2 为什么 KV Cache INT8 几乎 2x 容量，但 TTFT/TPOT 损失极小？

| 原因 | 解释 |
|------|------|
| **内存带宽瓶颈** | Decode 阶段是 **memory-bound**，KV Cache 读取占主导。INT8 减半带宽直接加速 |
| **反量化开销极低** | `dequant = q * scale`，在寄存器内完成，不额外访存 |
| **GEMM 本身不变** | Attention 的 Q·K^T 和 Softmax·V 仍是 FP16/BF16 计算，只 KV Cache 存储为 INT8，读取时即时反量化 |
| **TTFT 影响小** | Prefill 阶段 compute-bound，但 KV Cache 量化主要影响 Decode 的访存；且 Prefill 时 KV 是新生成的，量化写入是异步的 |
| **TPOT 几乎无损** | Decode 的 Attention 计算量小（seq_len 逐增），瓶颈在加载 KV Cache，INT8 直接减半加载时间 |

### 2.3 长上下文下 per-channel 为什么容易崩？

```python
# 核心原因：channel 分布在长序列上极度不稳定
# 假设 head_dim=128，每个 channel 是一个固定位置的特征维度

# 问题1：Token 动态范围变化
# 早期 token 的 KV 值范围小，后期 token（尤其是长上下文）可能因 attention 累积产生大值
# per-channel scale 是在整个序列上统计的，前期 token 用后期的大 scale 量化，有效位数被压缩

# 问题2：Outlier Channel
# 某些 channel 维度（如 RoPE 的特定频率）天然有更大的值，形成 outlier
# 这些 outlier 拉大了整个 channel 的 scale，导致其他 token 在该 channel 上精度骤降

# 问题3：Attention 误差累积
# KV 量化误差在 attention 中通过 softmax 加权求和累积，per-channel 的系统性偏差会沿 seq_len 放大
```

## 三、Activation Quantization：为什么比 Weight 更难？

### 3.1 核心难点

| 难点 | 说明 |
|------|------|
| **动态范围大** | Weight 分布固定（训练后静态），Activation 随输入变化，动态范围难以预测 |
| **Outlier 问题** | 某些 token/channel 出现极大值（如 LLM 中 ~0.1% 的 token 有 >20 的 activation），破坏整体 scale |
| **分布不对称** | Activation 常有非零均值和偏态，symmetric quantization 会浪费编码空间 |
| **逐层误差累积** | 前层 activation 量化误差传入后层，被网络放大 |

### 3.2 Outlier 处理方案

```python
# 方案1：Clipping（直接截断，牺牲少量 outlier 精度）
def clip_outliers(x, clip_ratio=0.999):
    flat = x.abs().flatten()
    k = int(clip_ratio * flat.numel())
    threshold = flat.kthvalue(k).values
    return x.clamp(-threshold, threshold)

# 方案2：SmoothQuant（迁移难度：activation -> weight）
# 核心公式：x' = x / s,  w' = w * s
# 让 activation 变得更易量化，把难度迁移到 weight（weight 对缩放更鲁棒）
def smoothquant_scale(x, w, alpha=0.5):
    # x: [token, hidden], w: [hidden, out]
    x_max = x.abs().max(dim=0).values  # per-channel
    w_max = w.abs().max(dim=1).values  # per-channel
    scale = (x_max ** alpha) / (w_max ** (1 - alpha))
    scale = scale.clamp_min(1e-6)
    return scale

# 方案3：LLM.int8() 的混合精度（>threshold 的用 FP16，其余 INT8）
# 这是工程上最稳的方案，但 kernel 复杂
```

## 四、Symmetric / Asymmetric Quantization

```python
def symmetric_quantize(x, num_bits=8):
    """
    Symmetric: zero_point = 0
    范围: [-2^(b-1), 2^(b-1)-1]
    适合: 近似零均值分布（如 weight、部分 activation）
    """
    qmax = 2 ** (num_bits - 1) - 1
    scale = x.abs().max() / qmax
    q = torch.round(x / scale).clamp(-qmax - 1, qmax)
    return q.to(torch.int8), scale

def asymmetric_quantize(x, num_bits=8):
    """
    Asymmetric: zero_point != 0
    q = clamp(round((x - xmin) / scale) + z)
    适合: 非零均值、偏态分布（如 ReLU 后的 activation、Post-LN 输出）
    """
    qmin = 0
    qmax = 2 ** num_bits - 1
    xmin, xmax = x.min(), x.max()
    scale = (xmax - xmin) / (qmax - qmin)
    zero_point = qmin - torch.round(xmin / scale)
    q = torch.round((x - xmin) / scale) + zero_point
    q = q.clamp(qmin, qmax)
    return q.to(torch.uint8), scale, zero_point

# 为什么 LLM 里 symmetric 更常用？
# 1. 零点是 0，kernel 里不需要额外加 zero_point（省指令）
# 2. Weight 通常经过 LayerNorm/ RMSNorm，近似零均值
# 3. INT8 GEMM 硬件（Tensor Core）对 symmetric 更友好
```

## 五、Group-wise Quantization：Group Size 的影响

```python
def groupwise_quantize(x, group_size=128, num_bits=4):
    """
    x: [..., in_features]，在 in_features 维度上切分 group
    每 group 有自己的 scale (和 optional zero_point)
    """
    orig_shape = x.shape
    in_features = orig_shape[-1]
    assert in_features % group_size == 0
    
    # reshape to [..., num_groups, group_size]
    x_reshaped = x.reshape(-1, in_features // group_size, group_size)
    
    # per-group max
    x_min = x_reshaped.amin(dim=-1, keepdim=True)
    x_max = x_reshaped.amax(dim=-1, keepdim=True)
    
    scale = (x_max - x_min) / (2 ** num_bits - 1)
    zero_point = -torch.round(x_min / scale).clamp(0, 2 ** num_bits - 1)
    
    q = torch.round(x_reshaped / scale + zero_point).clamp(0, 2 ** num_bits - 1)
    q = q.to(torch.uint8 if num_bits <= 8 else torch.int16)
    
    # reshape back
    q = q.reshape(orig_shape)
    return q, scale, zero_point
```

### Group Size 对精度 vs 性能的影响

| Group Size | 精度 | 显存 overhead | Kernel 性能 | 适用场景 |
|------------|------|---------------|-------------|----------|
| **per-tensor** (inf) | 最差 | 0 | 最快 | 快速实验 |
| **1024** | 较差 | 极小 | 很快 | 超大模型快速推理 |
| **128** | 好 | 小 | 快 | **AWQ/GPTQ 默认**，平衡首选 |
| **64** | 很好 | 中 | 中等 | 追求精度 |
| **32** | 极好 | 较大 | 较慢 | 小模型或对精度敏感 |
| **per-channel** (1) | 理论最好 | 大 | 慢/复杂 | 通常不用，overhead 过高 |

**关键权衡**：
- 越小 → 粒度越细 → 精度越高，但 **scale 元数据** 越多（显存 overhead ↑）
- 越小 → GPU 上并行度越低（每个 thread 处理的元素少），**指令开销占比上升**
- **128 是 sweet spot**：4-bit 下每组 128 个元素，scale 用 FP16 存，overhead = 128*4 / (128*4 + 16) ≈ **0.4%**，几乎可忽略

## 六、反量化路径：两种策略的 Shape 依赖

### 6.1 两种路径对比

```python
# 路径 A：Fused Dequant + GEMM（推荐，compute-bound 场景）
def fused_dequant_gemm(qweight, scales, x_fp16):
    """
    qweight: [out_features, in_features] int4/uint4
    scales: [out_features, num_groups] fp16
    x_fp16: [batch, in_features] fp16
    
    在 GEMM 内部，每个 MMA (Matrix Multiply Accumulate) 指令周期内：
    1. 从 shared memory 加载 4-bit weight 到寄存器
    2. 在线反量化为 FP16 (q * scale)
    3. 直接与 FP16 activation 做 FMA
    
    优点：不额外写回 FP16 weight，省带宽
    缺点：需要专用 kernel（Marlin/ExLlama/cutlass）
    """
    pass  # 由 CUDA kernel 实现

# 路径 B：先 Dequant 到 FP16，再 GEMM（通用，memory-bound 场景）
def dequant_then_gemm(qweight, scales, x_fp16):
    """
    1. 先把 qweight 反量化为 FP16 weight_full: [out_features, in_features]
    2. 调用标准 cuBLAS GEMM: output = x_fp16 @ weight_full.T
    
    优点：可用任何 GEMM backend（cuBLAS, torch.matmul）
    缺点：反量化后的 FP16 weight 需要额外显存/带宽
    """
    weight_fp16 = qweight.float() * scales  # 反量化
    return torch.matmul(x_fp16, weight_fp16.T)
```

### 6.2 为什么不同 Shape 下策略不同？

| 场景 | 推荐策略 | 原因 |
|------|----------|------|
| **大 batch (prefill)** | 路径 B 或 Fused | Prefill 是 compute-bound，GEMM 占主导，dequant 开销被掩盖 |
| **小 batch / decode** | **路径 A (Fused)** | Decode 是 memory-bound，weight 读取是瓶颈。Fused 避免写回 FP16，省 50% weight 带宽 |
| **weight 极小 (如 LoRA B)** | 路径 B | kernel launch overhead > fused 收益，直接反量化更省 |
| **per-channel / per-group** | 路径 A | scale 粒度细，必须在 load 时动态反量化，无法提前 dequant |

**核心原则**：
- **Memory-bound**（decode, 小 batch）→ 必须 fused，减少 weight 搬运
- **Compute-bound**（prefill, 大 batch）→ dequant 开销占比低，两种都可

## 七、AWQ + Marlin 完整推理链路

这是你最关心的部分。AWQ-Marlin 是**当前 W4A16 推理的最快方案之一**。

### 7.1 整体架构

```
Input (FP16/BF16) 
    ↓
[Linear Layer]
    ├── Weight: INT4 (已重排)
    ├── Scales: FP16 (per-channel 或 per-group)
    ├── Zeros: FP16 (optional, asymmetric 时)
    │
    ↓  [Marlin Kernel]
    1. 加载 4-bit weight tile (重排后的布局)
    2. 在线反量化到 FP16/BF16
    3. 与 activation 做 MMA (Matrix Multiply Accumulate)
    ↓
Output (FP16/BF16)
```

### 7.2 权重重排（Weight Reordering）详解

Marlin 使用 **2:4 稀疏风格的半结构化布局** 来优化 Tensor Core 访问模式。

```python
# 概念性展示（实际由 CUDA 代码完成）
def marlin_repack_weights(qweight, scales, group_size=128):
    """
    qweight: 原始 [out_features, in_features] 4-bit weight
    scales: [num_groups] or [out_features, num_groups]
    
    重排目标：让连续 16/32 个 4-bit 元素在内存中交错，
    使得一个 warp 的 32 个线程可以协作解包一个 weight tile，
    每个线程负责一部分，避免 bank conflict。
    """
    out_features, in_features = qweight.shape
    
    # Step 1: 将 4-bit 打包成 8/16/32-bit 容器
    # 两个 4-bit 组成一个 uint8
    # Marlin 使用 16x16 tile 结构匹配 Tensor Core
    
    # Step 2: 交错重排（Interleaved Reordering）
    # 原始布局: [out_f, in_f]
    # 重排后: [in_f/16, out_f/16, 16, 16] 或类似 tile 结构
    # 关键：让同一 warp 访问的 weight 在 shared memory 中连续
    
    # Step 3: Scale 打包
    # scales 与 weight tile 对应，存储在相邻位置
    # 实现 coalesced memory access
    
    return repacked_qweight, repacked_scales
```

**重排的核心目的**：
1. **Tensor Core 对齐**：每个 warp 一次处理 16x16x16 的 MMA，weight 必须按 `m16n8k16` 或 `m16n8k8` 布局排列
2. **避免 bank conflict**：4-bit 元素交错存储，32 线程同时读取时不撞 bank
3. **Scale 共置**：每个 weight tile 的 scale 放在紧邻位置，L2 cache 友好

### 7.3 融合反量化 + GEMM（Fused Dequant-GEMM）内核逻辑

```python
# 这是伪代码，展示 Marlin CUDA kernel 的核心逻辑
def marlin_kernel(x, qweight, scales, zeros, M, N, K, group_size):
    """
    x: [M, K] FP16 activation
    qweight: [K/2, N] uint8 (两个 4-bit  pack 成一个 uint8)
    scales: [K/group_size, N] FP16
    zeros: [K/group_size, N] FP16 (optional)
    
    Tile size: 通常 16x64 或 16x128
    """
    
    # 每个 block 处理 output 的一个 tile
    for m_block in range(0, M, 16):
        for n_block in range(0, N, 64):
            
            # 1. 从 global memory 加载 activation tile [16, K] 到 shared memory
            #    使用 cp.async 或标准 load，做 swizzle 避免 conflict
            
            # 2. 从 global memory 加载 weight tile [K, 64] (INT4 packed)
            #    每个线程加载 4/8 个 uint8，包含 8/16 个 4-bit weight
            
            # 3. 在线解包 + 反量化（寄存器内操作）
            for k_step in range(0, K, 16):
                # 加载 uint8
                packed = load_uint8(qweight, k_step, n_block)
                
                # 解包成两个 4-bit (low/high 4 bits)
                w_low = (packed & 0x0F).to_fp16()   # [0, 15]
                w_high = (packed >> 4).to_fp16()    # [0, 15]
                
                # 反量化（symmetric 示例）
                # 注意：Marlin 通常使用 0-centered 4-bit: [-8, 7] 或 [0, 15]
                # 这里假设 [0, 15] 需要减去 8
                w_low = (w_low - 8) * scale
                w_high = (w_high - 8) * scale
                
                # 4. MMA (Matrix Multiply Accumulate)
                # 使用 HMMA (FP16 Tensor Core) 指令
                # acc += x_tile @ w_tile.T
                
            # 5. 写回 output [M, N]
            store_output(acc, m_block, n_block)
```

### 7.4 AWQ 在 Marlin 中的特殊处理

AWQ 相比普通 W4A16，多了一个 **per-channel scaling factor**（保护 salient channels）：

```python
# AWQ 量化公式（simplified）
# 原始: Y = X @ W^T
# AWQ: 先对 W 做 per-channel 缩放: W' = W * s，其中 s 是 activation 幅度的函数
#      然后量化 W' 为 4-bit
#      推理时: Y = X @ (W_q / s)^T = X @ W_q^T * (1/s)

# 在 Marlin 中，这个 (1/s) 被 fuse 到 dequant 阶段：
# dequantized_w = (q_w - zp) * scale * awq_scale

# 所以 AWQ-Marlin 的 weight 布局：
# [packed_qweight | marlin_scale | awq_scale]
# 或两者合并为一个 effective_scale
```

```python
import torch
import torch.nn as nn

# ============================================================
# 1. 基础量化函数
# ============================================================

def quantize_per_token_per_head(kv, eps=1e-6):
    """
    KV Cache 量化：per-token per-head
    kv: [num_tokens, num_heads, head_dim]
    返回: q (int8), scale (fp16)
    """
    # amax over head_dim
    scale = kv.abs().amax(dim=-1, keepdim=True).clamp_min(eps) / 127.0
    q = torch.round(kv / scale).clamp(-128, 127).to(torch.int8)
    return q, scale

def dequantize_per_token_per_head(q, scale):
    """反量化"""
    return q.float() * scale

# ============================================================
# 2. AWQ 核心：Salient Channel 保护
# ============================================================

def awq_quantize(w, x_act, num_bits=4, group_size=128):
    """
    w: [out_f, in_f] weight
    x_act: [N, in_f] 校准 activation
    """
    # 1. 计算 per-channel activation 幅度
    act_scale = x_act.abs().mean(dim=0)  # [in_f]
    
    # 2. 保护 salient channels：放大这些 weight
    # 等价于：对难量化的 channel 给更多"有效位"
    w_scaled = w * act_scale.unsqueeze(0)
    
    # 3. Group-wise 量化 w_scaled
    in_f = w.shape[1]
    num_groups = in_f // group_size
    
    w_reshaped = w_scaled.reshape(-1, num_groups, group_size)
    w_max = w_reshaped.abs().amax(dim=-1, keepdim=True)
    
    scale = w_max / (2 ** (num_bits - 1) - 1)
    q = torch.round(w_reshaped / scale).clamp(
        -(2 ** (num_bits - 1)), 2 ** (num_bits - 1) - 1
    )
    
    # 4. 记录 awq_scale (用于推理时反除)
    # 实际推理: y = x @ (q * scale / act_scale)^T
    return q, scale, act_scale

# ============================================================
# 3. Group-wise 量化 + 反量化
# ============================================================

def group_quantize(w, group_size=128, num_bits=4):
    orig_shape = w.shape
    in_f = orig_shape[-1]
    assert in_f % group_size == 0
    
    w_r = w.reshape(-1, in_f // group_size, group_size)
    wmin = w_r.amin(dim=-1, keepdim=True)
    wmax = w_r.amax(dim=-1, keepdim=True)
    
    qmax = 2 ** num_bits - 1
    scale = (wmax - wmin) / qmax
    zp = -torch.round(wmin / scale).clamp(0, qmax)
    
    q = torch.round(w_r / scale + zp).clamp(0, qmax)
    return q.reshape(orig_shape), scale, zp

# ============================================================
# 4. SmoothQuant 迁移
# ============================================================

def smoothquant(x, w, alpha=0.5):
    x_max = x.abs().max(dim=0).values  # [in_f]
    w_max = w.abs().max(dim=1).values  # [out_f] -> 需要对齐，实际用 per-channel
    # 简化版：假设 per-tensor 或 per-channel 已处理
    scale = (x_max ** alpha) / (w_max ** (1 - alpha) + 1e-6)
    x_smooth = x / scale
    w_smooth = w * scale.unsqueeze(0)
    return x_smooth, w_smooth

# ============================================================
# 5. 验证：量化误差分析
# ============================================================

if __name__ == "__main__":
    torch.manual_seed(42)
    
    # 测试 KV Cache 量化
    kv = torch.randn(1024, 32, 128)  # [tokens, heads, dim]
    q, scale = quantize_per_token_per_head(kv)
    kv_rec = dequantize_per_token_per_head(q, scale)
    print(f"KV quant error (per-token-per-head): {(kv - kv_rec).abs().mean():.6f}")
    
    # 测试 group-wise
    w = torch.randn(4096, 4096)
    q_g, s_g, zp_g = group_quantize(w, group_size=128, num_bits=4)
    w_rec = (q_g.reshape(-1, 32, 128).float() - zp_g) * s_g
    w_rec = w_rec.reshape(4096, 4096)
    print(f"Group-wise W4 error: {(w - w_rec).abs().mean():.6f}")
```

## 十、Marlin 权重布局补充（工程细节）

Marlin 的 weight 不是简单的 `uint8` 数组，而是经过**两步重排**：

```
原始 Weight: [N=4096, K=4096] int4
    ↓
Step 1: Pack
    每 2 个 int4 -> 1 个 uint8
    [N, K/2] uint8
    ↓
Step 2: Tile & Interleave (Marlin 特有)
    将矩阵切分为 16x64 tiles
    在 tile 内部，数据按 warp 访问模式交错排列
    最终布局: [K/16, N/64, 16, 64/2] 的某种变体 (具体取决于版本)
    ↓
Step 3: Scale Co-location
    每个 tile 对应的 scale 放在 weight 数组的尾部或交错位置
    使得一个 L2 cache line 能同时拿到 weight 和 scale
```

**为什么重排后更快？**
- NVIDIA Tensor Core 的 `mma.sync.aligned.m16n8k16.row.col.f16.f16.f16` 指令要求 A 矩阵按行主序 16 连续，B 矩阵按列主序 16 连续
- Marlin 的重排确保每个 warp 的 32 线程在加载一个 tile 时，访存地址是**连续且对齐**的
- 4-bit 解包后直接在寄存器里做 FP16 MMA，不需要写回 shared memory
